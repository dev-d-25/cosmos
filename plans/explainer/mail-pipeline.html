Mail Pipeline — How data flows from Gmail to the UI

The full data path: Gmail API → Corsair SDK → DB → page assembly → React. Covers the three fetch tiers, window backfill, and the per-page enrichment cycle.

TL;DR Gmail messages flow through three tiers: (1) bulk window backfill pulls 500 IDs then enriches each via messages.get(format=metadata), (2) page assembly reads the DB at the requested offset and enriches any remaining stubs inline, (3) clicking a message triggers a full messages.get(format=full) fetch. The DB is the source of truth after tier 1; tiers 2 and 3 never bypass it.

1. The three fetch tiers

Tier When Gmail call DB write
TIER 1 Window backfill On-demand when page is empty (cold start), or via background refresh messages.list(maxResults=500) → IDs only
messages.get(id, format=metadata) × N		 upsertManyByEntityIds — stores subject, from, to, labelIds, snippet, internalDate
TIER 2 Page assembly Every page load (DB read is the fast path) None (DB read only). If stubs found, enriches inline via messages.get(format=metadata) Only if stubs were enriched (rare after tier 1 ran)
TIER 3 Message detail User clicks a message messages.get(id, format=full) SDK auto-upserts the full payload (body HTML/text, attachments)

2. Cold start vs warm start

Cold start = the DB has zero messages for this view (or the page is empty). The pipeline triggers on-demand window backfill to populate the DB before serving.

Warm start = the DB already has enriched messages at the requested offset. The pipeline reads from DB and returns immediately — no Gmail call at all.

Cold start flow

flowchart TD
    A[GET /api/mail?page=1] --> B[assemblePageWithBackfill]
    B --> C[assemblePage → assembleInbox]
    C --> D{DB has rows at offset?}
    D -- "Yes (warm)" --> E[Return from DB]
    D -- "No (cold)" --> F[backfillWindow]
    F --> G["messages.list(maxResults=500)"]
    G --> H[Get IDs + nextPageToken]
    H --> I["enrichStubs(ids)"]
    I --> J["messages.get(id, format=metadata) × N"]
    J --> K[upsertManyByEntityIds]
    K --> L[persist nextPageToken]
    L --> M{rows now at offset?}
    M -- "Yes" --> N[Return from DB]
    M -- "No" --> O{windows < MAX_WINDOWS?}
    O -- "Yes" --> F
    O -- "No" --> P[Return empty]

Warm start flow

flowchart TD
    A[GET /api/mail?page=1] --> B[assemblePageWithBackfill]
    B --> C[assemblePage → assembleInbox]
    C --> D{DB has rows at offset?}
    D -- "Yes" --> E[listByLabel from DB]
    E --> F[Filter enriched rows]
    F --> G[Sort by receivedAt desc]
    G --> H[Build page meta + count]
    H --> I[Return MailListResponse]

3. Window backfill — the 500-stub pipeline

The core of tier 1. Called by mail-ingestion.ts:backfillWindow(). Each window is exactly one Gmail messages.list call (max 500 IDs), followed by per-message enrichment.

Why two steps?

Gmail's messages.list only returns {id, threadId}. The format and metadataHeaders params are silently ignored on messages.list. To get Subject/From/To/Date, we must call messages.get for each ID individually.

flowchart LR
    subgraph "Step 1: List"
        A["messages.list(maxResults=500)"] --> B["{id, threadId} × 500"]
    end
    subgraph "Step 2: Enrich"
        B --> C["messages.get(id, format=metadata)"]
        C --> D["{id, labelIds, snippet, payload.headers}"]
    end
    subgraph "Step 3: Persist"
        D --> E["upsertManyByEntityIds"]
        E --> F[(DB)]
    end

Window chaining

Each window returns a nextPageToken. This token is persisted in mail_sync_state (per account + view key) so the next window can resume from where the previous one left off. Chaining is bounded by MAX_WINDOWS = 5 (2500 messages max per request).

4. Page assembly — the fast path

mail-page-assembly.ts:assembleInbox() reads from the DB at the requested offset. No Gmail call unless stubs are found.

flowchart TD
    A[assembleInbox] --> B["listByLabel(INBOX, limit=25, offset)"]
    B --> C{Rows found?}
    C -- "No" --> D[Return empty page]
    C -- "Yes" --> E{Any un-enriched stubs?}
    E -- "No" --> F[Filter enriched → sort → build meta]
    E -- "Yes" --> G[enrichStubs for stub IDs]
    G --> H[Re-read from DB]
    H --> F
    F --> I[Return MailListResponse]

5. Message detail — tier 3

mail-messages.ts:getMessage() handles the click-to-open flow.

flowchart TD
    A[getMessage(id)] --> B{force=true?}
    B -- "Yes" --> C["fetchMessageFull(id, format=full)"]
    B -- "No" --> D[findByEntityId from DB]
    D --> E{Cached row has body?}
    E -- "Yes" --> F[Return from cache]
    E -- "No" --> C
    C --> G["SDK messages.get(format=full)"]
    G --> H[SDK auto-upserts to DB]
    H --> I[Return from live fetch]

Note: The SDK's messages.get auto-upserts the full record to the DB. fetchAndPersistFullBody no longer calls upsertManyByEntityIds directly — the SDK handles it internally via its own entity schema.
